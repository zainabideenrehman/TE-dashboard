Then read ONLY the 1-2 anchor project files the index points to for this job.
Use `briefing.md` in the current folder for context. Write the result to

## Rules
- MAX 5 PAYLOADS. A payload is one distinct idea the reader has to absorb. This
  is the PRIMARY constraint and the one that governs whether a proposal reads
  dense. Count them before writing. If the draft carries more than five, cut
  ideas. Do NOT compress words. Eight ideas squeezed into 250 words is the most
  common failure of this command, and it produces copy where every sentence is
  load-bearing and nothing is skimmable.
- Word count follows from payload count. 150-220 typical, 250 hard ceiling (P.S.
  counted). At 250 words with five payloads the writing is fine. At 250 with
  eight, cut two ideas rather than trimming adjectives.
- Length scales INVERSELY with attached assets. A Loom or lead magnet carries
  payload on its own, so the proposal gets SHORTER, not longer. With a Loom
  attached, target 150-190 and let the video hold the technical reasoning.
- Leave one low-information sentence per proposal. A short connective line that
  costs nothing to read ("Same shape as your problem.") gives the reader a beat
  and makes the sentences around it land. Copy where 100% of lines carry weight
  is exhausting to read.
- Reading level: BELOW 3rd grade on WORD choice. This is stricter than the
  "third-grade" baseline in voice-rules.md and overrides it for proposals. Aim
  for 1st-2nd grade words and one main point per sentence. But VARY the rhythm:
  mostly short sentences, with some longer ones that connect using "and / so /
  but / because". Do NOT chop everything into uniform fragments. That drumbeat
  is the thing that makes a proposal sound like AI. See "Sound human" in
  voice-rules.md and run the read-aloud test before output.
- All other voice rules apply. Scan for "—" and "--" before output. Zero allowed.
- Budget under $1K: 100 words max, framed as a quick win.
- 90% client / 10% Hassan. Never flip it.

## Structure — 5 parts in order

Sentence counts below are CEILINGS, not quotas. A part finished in one sentence
is finished. Never pad a part to fill its allowance. Permitted merges:
- Parts 4 and 5 may collapse into a single close when the P.S. insight is the
  CTA.
- Part 2's tech-choice reasoning may be dropped entirely when a Loom or lead
  magnet carries it. The first move still stays.
- Part 1's deeper pain point may live in one clause rather than its own
  sentence.

1. HOOK (2-3 sentences). Say their problem back to them in plain words. Then
   show the deeper pain point you understand, the WHY under the surface ask.
   Use client's first name if known.
2. THE SOLUTION (2-4 sentences). How you'll solve their problem. Concrete first
   move. Specific tech choices WITH reasoning, not just stack names.
3. SAVE THE DAY (2-3 sentences). Map REAL portfolio experience that proves you
   have done it before. Never fabricate. NAME the project and LINK its app URL
   or the client's website. Pull the URL from portfolio/_index.md or the case
   study. NEVER reference a project vaguely ("for one brand I built...",
   "another client in this space"). If a project genuinely has no public URL
   (e.g. AutoCar link TBD, or a confidential client), name it without a link,
   but prefer a linkable anchor when one fits equally well. Automotive = lead
   with AutoCar (mandatory). Same-industry client is the ONE exception to
   naming: tease, don't name (don't reveal you work with their competitor), and
   link a different, non-competing project instead.
4. THE CTA (1-2 sentences). Tell them exactly what to do. If a Loom link
   exists: "I put together a quick walkthrough of how I'd approach this:
   [loom link]. If it resonates, hit reply and we can jump on a call."
5. THE P.S. (1-2 sentences). Genuinely personalized: urgency, observation,
   bonus insight, or motivation. If it could apply to any job, rewrite it.

## Edge cases
- Vague brief: proposal asks ONE clarifying question that shows expertise.
- Invite (not application): slightly warmer, more direct close
  ("when works for a quick call this week?").
- Tech he hasn't used: "I haven't used [X] directly but I've built similar
  things with [Y]."

## Final check before output
Run this as an actual pass over the draft, not a mental nod. Count the payloads
first: if there are more than five, delete ideas before touching anything else.

5 payloads or fewer / one low-information connective sentence present /
under 250 words / below 3rd grade reading level / VARIED sentence rhythm (read
it aloud, no drumbeat) / no antithesis spam ("not X, but Y") / no template-seam
openers ("Here's my first move") / no over-explained benefit tails / no banned buzzwords / zero
em dashes / no exclamation marks / first name used if known / hook names their
problem then the deeper pain / solution comes before save-the-day / real
experience only / every named project linked (URL from _index.md or case study)
/ no vague project references / AutoCar if automotive / Ludooka if kids edu /
same-industry teased not named / concrete solution / clear CTA / personalized
P.S. / 90-10 ratio.
